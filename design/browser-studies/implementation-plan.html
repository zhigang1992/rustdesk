Option A: a browser workspace for each computer

Selected direction: a compact horizontal tab strip, with the address field inside the selected website tab. Website tabs and a screen-sharing tab belong to one computer workspace. The computer picker switches the whole workspace.

View the interactive mockups — select A, Browser-first.

Recommended first delivery: iOS and iPadOS, behind a Dev-only opt-in until validated. Keep the existing Mac host and routing protocol. Deliver the browser shell first, then integrate the Flutter desktop as a tab. Production implementation has not started.

Product behavior

  • Launch into the last-used computer workspace and a New tab page. If no computer is saved, show Add computer within that page. Restore the workspace before connecting; connect when a remote page or desktop needs it, using existing authentication.
  • One compact app toolbar above content. On iPad: Back, Forward, tabs, New tab, bookmark and menu actions. The selected tab expands into the address field and contains the computer chip. Inactive tabs show page titles and a close action. Screen sharing shows a monitor icon and “Desktop.”
  • On narrow iPhone layouts, keep the same concept with the selected address, Back, tab count and menu. Put other tabs in the overview and secondary actions in the menu. Do not compress every desktop control into tiny buttons.
  • Switching computers restores that computer’s selected tab, website views, bookmarks and in-memory Back/Forward stacks. Editing a URL navigates only the selected website tab. It never changes the computer.
  • A New tab page contains favorites, recent pages and an Open desktop action for the current computer. Adding or switching computers is available from the computer picker.
  • Desktop selection disables website navigation controls. Switching away keeps its connection, but releases remote input focus, keyboard capture and active gestures. Closing Desktop ends only screen sharing. Closing the last website tab creates a blank tab in that workspace.
  • Disconnects show an inline state with Reconnect. Saved tabs and cookies remain. No repeated automatic navigation loop and no silent direct-network fallback.

Architecture

Flutter workspace shell — toolbar, tab selection, New tab, computer picker ├─ Website content: native WKWebView through an iOS platform view └─ Desktop content: existing Flutter RemotePage and Control Pad Workspace connection owner — dedicated existing browser FFI/tunnel session Native browser owner — WKWebViews, WebKit navigation, per-host website data Persistent workspace metadata — selected tab, saved URLs, bookmarks, recents

This is a recommendation pending a device spike. Flutter supports embedding native UIKit views using platform views; the official guide also documents composition and performance trade-offs. Validate against this repository’s pinned SDK rather than introducing an SDK upgrade as part of the UI work. Flutter iOS platform-view documentation.

Flutter owns presentation metadata; WebKit remains the authority for website URL, title, loading state and Back/Forward. Exchange commands and events over the existing plugin channel, with explicit workspace/tab IDs. Do not maintain a second navigation stack in Dart. Reuse the native browser behavior and add an embedded mode with its own toolbar hidden; preserve the current modal mode as the fallback.

Move browser-transport lifetime out of the transient browser route into a feature-specific workspace owner. View attachment and tab selection must not close it. Only explicit workspace disconnect or owner disposal closes its tunnel. Keep browser tunnels separate from the desktop connection, as they are today.

Persistence and compatibility

The current native implementation already isolates website data using profileID(for: peerIdentity) and saves tabs/bookmarks under that identity. Keep that exact mapping and migrate tab metadata additively. Do not replace it with a display name, IP address or a new UUID scheme. These are this app’s browser cookies; they are not the Mac’s Safari/Chrome cookies.

Retained WKWebViews preserve Back/Forward during normal tab/workspace switches. The current persisted state stores URLs, not full navigation stacks. First-release restart recovery promises URLs, selected tab, bookmarks and website data; full Back/Forward history across process termination is outside that promise. A recent-pages list is separate from WebKit’s live navigation stack.

Keep existing iOS availability checks. Remote browsing currently starts at iOS 17; the loopback routing extension uses an iOS 18.4 capability. This redesign must not imply broader localhost support or raise the entire app’s minimum deployment target.

First-release limits

  • One live screen-sharing session across the app. Mobile RemotePage uses global gFFI. Switching computer workspaces can leave the current desktop connected but hidden. Opening another computer’s desktop must ask to end the existing one. Supporting concurrent desktops requires a separately scoped session-isolation change.
  • Website tabs for different computers remain isolated. Apply the existing tab cap to each native workspace and validate memory use with two realistic workspaces. If WebKit terminates a content process, recover the selected page with a clear reload state; do not promise an intact live history after eviction.
  • Focus on iOS/iPadOS. The Mac remains the host. A Mac browser client with the same shell needs a macOS WebKit adapter and separate validation later.
  • No browser sync, extensions UI, download manager, incognito mode, system VPN, or proxy-protocol redesign in this delivery.

Acceptance checks

  • Real iPad Air: Google and the existing http://localhost:50100/login/phone verification flow still work, including cookies, redirects, API calls and WebCrypto.
  • Two computer workspaces with identical localhost addresses do not mix content, cookies, bookmarks or recent pages. Reconnect retains the same profile.
  • Desktop keyboard, Control Pad and touch optimizations continue working; typing in a web form/address or switching tabs sends nothing to the remote desktop.
  • Existing saved tabs/bookmarks survive upgrade; desktop sessions never reconnect automatically solely because persisted metadata exists.
  • Use focused Flutter tests for workspace selection, close behavior and deep-link routing; run existing browser link and routing tests. Validate native composition and real networking on device without adding a new test framework.

Implementation order: prove native/Flutter composition first → deliver browser-only A → add workspace switching → add desktop tabs → make it the opt-in launch experience. Review the final diff for each stage; keep unrelated paths unchanged.
